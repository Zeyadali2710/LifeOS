## Fixed Issues

### CR-01: Projects whose only linked data is a dependency edge can't be deleted

**Files modified:** `src/projects/project-workspace.tsx`, `src/server/projects.ts`, `tests/db/project-actions.test.ts`
**Commit:** 1f65222
**Applied fix:** The workspace delete dialog now always sends `confirmUnlink=true`, because the user has already confirmed. The server guard stays in place for other callers. The `has_linked_data` counts now include `dependencies` (edges in either direction). Added a db test for a project whose only linked data is a dependency edge: it is refused without confirmation, the refusal reports `dependencies: 1`, and it deletes with confirmation. I did not add `dependents` to the DTO or the confirm body. The fix doesn't need it.

### WR-01: Tasks in an archived project can still be toggled and edited

**Files modified:** `src/projects/project-tasks.tsx`
**Commit:** c9948f1
**Applied fix:** The task Checkbox and the title button that opens TaskDialog now take `disabled={readOnly}`. This is a client-side gate only. The server still accepts task mutations on archived projects, which matches how milestones already work.

### WR-02: Unarchiving always sets status to "active" and loses paused/done

**Files modified:** `src/server/db/schema.ts`, `drizzle/0006_project_archived_from.sql`, `drizzle/meta/0006_snapshot.json`, `drizzle/meta/_journal.json`, `src/server/projects.ts`, `tests/db/project-actions.test.ts`
**Commit:** cd10773
**Applied fix:** Added a nullable `projects.archived_from` column. The migration was generated by drizzle-kit and contains only the `ADD COLUMN`. Archiving through `setProjectArchived` or through `updateProject` with `status: "archived"` records the prior status, and re-archiving keeps the original value. Unarchiving restores it, falls back to `active`, and clears the column. I chose this over "unarchive to paused" because that option would have broken the e2e flow (archive, unarchive, then expect the project under Home's Active projects). Added a db test covering done -> archived -> done and paused -> archived (via update) -> paused. **Needs human verification:** this is a logic and schema change, and migration 0006 has to be applied on the VM.

### WR-03: Blocked-state transitions are not evented for task delete or for moving a task between projects

**Files modified:** `src/server/task-actions.ts`
**Commit:** dedebd7
**Applied fix:** `deleteTaskAction` and `updateTaskAction` now wrap the mutation in `withBlockTransition`. The affected projects are the task's own project, the downstream projects (same query as toggle) and, for an update, the new `projectId` when it is a valid uuid. Agent and other non-action callers of `updateTask`/`deleteTask` are still not evented. **Needs human verification:** logic change, and there is no dedicated test for the new events.

### WR-04: toggleTaskAction runs its pre-queries outside `run()`

**Files modified:** `src/server/task-actions.ts`
**Commit:** 5ee71ae
**Applied fix:** Moved the affected-project lookups into a private `affectedProjects()` helper that is called inside `run(...)`, so DB errors return `{ok:false,error:"failed"}` and get logged. WR-03 reuses the helper.

### WR-05: Task dialog keeps a stale `added` blocker list after a partial failure on a new task

**Files modified:** `src/organization/task-dialog.tsx`
**Commit:** 52e566a
**Applied fix:** After a partial save (a blocker or completion change failed after the task row was saved), the dialog does three things. It resets the dirty-check baseline to the saved state, so only the unsaved deltas count as dirty. It reloads dialog options for the saved task id, so the blocker list reflects what the server has; before this, successfully saved blockers disappeared from the list. It treats the saved new task like `task` for the Delete and Completed controls. **Needs human verification:** UI state logic with no automated test.
