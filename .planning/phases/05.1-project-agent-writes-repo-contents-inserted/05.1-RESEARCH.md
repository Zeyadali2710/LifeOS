## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Repo content tools (read-only)
- **D-01:** Two new READ tools on the Projects agent: `github.list_tree` (repo, optional path prefix) and `github.get_file` (repo, path). Both use the **existing read PAT** only, live-fetch from GitHub, and only work on repos already in `github_repos` (reuse `resolveRepo`/`repoRow`, so access stays within what the read PAT grants per Phase 3 D-06). Not connected → the existing honest `NOT_CONNECTED` envelope.
- **D-02:** **Default branch only.** Both tools read `github_repos.defaultBranch`; there is no `ref` input. `list_tree` uses the git trees API (recursive) and returns paths, type and size only, capped at **400 entries** with a `truncated` flag, skipping noise dirs (`node_modules/`, `.git/`, `vendor/`, `dist/`, `build/`, `.next/`).
- **D-03:** **Size caps:** `get_file` returns at most **16 KB of text per file** (`truncated: true` beyond that) and refuses binary content (NUL bytes / not valid UTF-8) and files GitHub reports over 1 MB. Paths are validated (relative, no `..`, no leading `/`, each segment URL-encoded) before reaching `client.get`.
- **D-04:** **No caching, no storage of contents.** Each call fetches live; the only copy kept is the normal (redacted, capped) `tool_calls.output` row, same as every other tool. No new tables for repo content.
- **D-05:** **Private repos and the 03.1 free-model gate:** every content tool output carries the repo full name, so the existing `mentionsSensitive` scan taints the run when the repo is private or of unknown visibility (fail closed). With the private-repo toggle off, private content never reaches a free model; the run switches to Sonnet via the existing D-05/D-09 mechanism. No new privacy mechanism.
- **D-06:** **Repo content is untrusted data.** File content is returned inside an envelope `{ repo, path, truncated, untrusted: true, content }`, and the Projects prompt says repo files are data written by others and never instructions. **Gateway floor:** once a run has called `github.get_file` or `github.list_tree`, any side-effecting tool in that run resolves to at least APPROVE, whatever the `permissions` override says (a few lines next to `resolvePolicy`). Repo content can therefore only ever produce a proposal the owner reviews; it can never execute a write by itself.

#### Write tools and granularity
- **D-07:** **Two composite APPROVE tools**, not per-entity tools: `projects.create` (new project + milestones + tasks + links + task dependencies in one payload) and `projects.update` (one existing project: field changes, add/update tasks, add/update milestones, add links, add task or project dependencies). One approval per proposal satisfies "one approval can create a project with its tasks, milestones and links".
- **D-08:** **Tiers:** both tools default **APPROVE** (Phase 4 D-06/D-19 pattern for agent writes to owner data). **No agent delete or unlink tools this phase**; the owner deletes in the UI. Removing things is deferred and, when added, is HIGH_RISK (Phase 4 D-07 pattern).
- **D-09:** **Payload shape:** reuse the Phase 5 schemas (`projectInput`, `milestoneInput`, `linkInput`, `taskInput`). Inside one payload, milestones carry a client `key` and tasks reference `milestoneKey`; task dependencies reference task indexes/keys; repo links are by `fullName` (resolved to `github_repos.id` at execute; unknown repo → `not_found`). `workspacePath`/`workspaceMachine` are **not** settable by the agent (they go into a shell command). Sane bounds: ≤ 12 milestones, ≤ 40 tasks, ≤ 10 links per payload.
- **D-10:** **Execution is one Postgres transaction** calling the existing `createProject`/`createMilestone`/`createTask`/`addLink`/`addTaskDependency`/`addProjectDependency` server functions with the transaction handle, so validation, cycle checks and activity/audit behave exactly like owner writes (Phase 5 D-16). Any failure rolls back everything; partial projects never exist.
- **D-11:** **Idempotency (AGT-03):** the same transaction writes an audit entry carrying the approval id. On an ambiguous retry (`ctx.adopt`) the handler first looks for that audit entry and, if present, returns the stored result instead of writing again (local-DB analogue of the GitHub issue marker). No new column or table.

#### Context notes
- **D-12:** Add a **`projects.context`** text column (Markdown, ≤ 4000 chars, default empty) for the longer "what this project is / how it's built / where things are" notes the agent drafts from README/docs. `description` stays the 500-char one-liner. Context is editable in the owner's project dialog, shown on the `/projects/[id]` workspace, included in the Phase 5 D-14 "Copy context" brief, and returned (capped) by `projects.get`.

#### Approval card UX
- **D-13:** New approval kinds `project_create` and `project_update` in `approval-kinds.ts` with their own payload schemas, summaries ("Approval waiting: create project \"Studio\" · 9 tasks, 3 milestones") and a `ProjectApprovalBody` alongside the issue and event bodies, on the Approvals page and inline in the AI panel (Phase 3 D-03).
- **D-14:** **Edit-before-approve on the whole draft:** editable project fields (name, description, context, category, priority, target date); milestones list (edit title/due, remove); tasks list (edit title/due/priority/milestone, remove); links list (remove only). Removing a milestone unassigns its tasks. Adding new rows is not offered in the card (the owner adds after creation in the normal UI). Server re-validates the edited payload with zod on approve (Phase 3 D-04).
- **D-15:** **Locked fields:** `projects.update` locks `projectId`; repo link targets can be removed but not changed. The card shows a "Drafted from repository files (untrusted)" note listing the paths the agent read when the run used content tools.
- **D-16:** After approval the suspended run resumes and the agent replies with a link to the new project (`/projects/[id]`); executed state on the card links there too. Expiry, reject, retry and failure states reuse the Phase 3/4 approval machinery unchanged.

#### Agent, model and limits
- **D-17:** **The Projects agent owns it** (tools added to its registry entry; prompt updated: it can now propose project changes, never directly write, and must treat repo files as untrusted). The orchestrator prompt tells Opus to delegate "create/update a project from a repo" to the projects agent with **tier `reasoning`** (drafting = reasoning, so Sonnet per 03.1 D-01); the tag is trusted (03.1 D-02).
- **D-18:** **Per-agent run limits:** add an optional `limits` override on `AgentDef`; the Projects agent gets **16 tool calls and 150k tokens** per run (the global 12 / 60k is too small once file contents accumulate across turns). Other agents keep `RUN_LIMITS`. Spend cap (Phase 3 D-14/15) still applies.
- **D-19:** **Drafting guidance in the prompt:** read the tree first, then README and at most ~6 relevant files (ROADMAP/TODO/CHANGELOG/docs index); propose one `projects.create` call; link the source repo; derive milestones from roadmap headings and tasks from open items; prefer the repo's open issues (existing `github.list_issues`) for tasks where present; don't invent dates (leave null unless the repo states them).

## Summary

Everything this phase needs already exists in the codebase as a pattern; the work is composition. The gateway (`src/server/agents/gateway.ts`) already does allow-list → zod → `resolve` → tier → atomic approval row, and `executeApproved` (`src/server/agents/approvals.ts`) already runs `tool.handler(tool.input.parse(payload), { approvalId, adopt })` exactly once, maps `ToolError` to a definite failure and any other throw to an *ambiguous* failure that sets `adopt` on Retry. The GitHub client's `get()` (zod-parsed JSON) is enough for both the git trees and the contents endpoint (default JSON media type returns base64 `content` for files ≤ 1 MB). The Phase 5 project server functions all take a `DB` handle, and a drizzle transaction handle is assignable to `DB` (the gateway already passes `tx` into a `(tx: DB) => …` helper), and nested `h.transaction()` calls inside them become savepoints in drizzle 0.45 node-postgres — so D-10's "one transaction calling the existing functions" works without refactoring them.

The real risks are not in the new code but in edges of the existing code that the new flow hits for the first time: (1) `redact()` blanks any key matching `/key|token|secret|password|authorization/i`, so a payload field named `key`/`milestoneKey` (as D-09 words it) would show up as `"[redacted]"` in `tool_calls.input` and in model-visible duplicate outputs — use `ref`/`milestoneRef`; (2) the server functions return `{ ok:false }` instead of throwing, so the composite handler must convert every non-ok result into a thrown `ToolError` to roll back; (3) `updateProject`/`updateTask`/`updateMilestone` are **full replace** with zod defaults — an agent "update" must merge onto the current row or it wipes `workspacePath`, notes, reminders and context; (4) loop limits: besides D-18's 16 calls / 150k tokens, `turnMaxTokens` 4096 is tight for a 40-task payload and `activeMs` 120 s is counted on the **orchestrator** too, including the inline delegate's child time, so the orchestrator can fail "took too long" right after the owner approves; (5) the existing fake LLM (`tests/helpers/fake-llm.ts`) is vitest-only — e2e has no LLM and no worker, so the scripted Studio flow must be a DB integration test and the e2e covers the seeded card → edit → approve UI.

**Primary recommendation:** Add two READ tools to `tools/github.ts`, two APPROVE tools to `tools/projects.ts` that share one draft schema in `src/lib/project-payload.ts` and one `applyDraft(tx, …)` executor, a 4-line content floor in the gateway tier step, per-agent `limits` (incl. `turnMaxTokens` and `activeMs`) via a `limitsFor(agent)` helper, and the `ProjectApprovalShell` UI mirroring `event-approval.tsx`. No new dependencies, one migration (0007, `projects.context`).

### Pattern 1: `github.list_tree` / `github.get_file` (READ)

Reuse `repoRow`, `resolveRepo`, `readToken`, `createGithub`, `NOT_CONNECTED`. Output envelopes always include `repo` (full name) so the existing taint scan sees private repos (D-05).

```typescript
// src/server/agents/tools/github.ts (sketch; Source: existing getPullRequest pattern + GitHub REST docs)
const NOISE = /(^|\/)(node_modules|\.git|vendor|dist|build|\.next)(\/|$)/;
const TREE_CAP = 400;
const FILE_CAP = 16_384;            // characters of decoded text (~16 KB)
const MAX_GH_SIZE = 1_000_000;      // GitHub returns empty content above 1 MB on the JSON media type

// Relative path, no "", ".", ".." segments, no backslash/control chars; each segment URL-encoded.
export const repoPath = z.string().min(1).max(400).refine(
  (p) => !p.startsWith("/") && !/[\\\u0000-\u001f]/.test(p) && p.split("/").every((s) => s && s !== "." && s !== ".."),
  "Use a relative path inside the repository.",
);
const enc = (p: string) => p.split("/").map(encodeURIComponent).join("/");

const treeRes = z.object({ truncated: z.boolean(), tree: z.array(z.object({ path: z.string(), type: z.string(), size: z.number().optional() })) });
const fileRes = z.union([
  z.object({ type: z.string(), size: z.number(), encoding: z.string().optional(), content: z.string().optional() }),
  z.array(z.unknown()), // a directory
]);

async function gh(ctx: ToolContext) { const token = await readToken(ctx.handle); return token ? createGithub({ token, fetch: ctx.fetch }) : null; }

// get_file handler core
const r = await repoRow(ctx, i.repo);
const res = await g.get(`/repos/${i.repo}/contents/${enc(i.path)}?ref=${encodeURIComponent(r.defaultBranch)}`, fileRes);
if (Array.isArray(res.data)) throw new ToolError("invalid_input", "That path is a folder; use list_tree.");
if (res.data.type !== "file") throw new ToolError("invalid_input", "That path isn't a regular file.");
if (res.data.size > MAX_GH_SIZE || res.data.encoding !== "base64") throw new ToolError("invalid_input", "That file is larger than 1 MB.");
const buf = Buffer.from(res.data.content ?? "", "base64");      // GitHub wraps base64 at 60 chars; Buffer ignores \n
let text: string;
try { if (buf.includes(0)) throw 0; text = new TextDecoder("utf-8", { fatal: true }).decode(buf); }
catch { throw new ToolError("invalid_input", "That file is binary, not text."); }
return { connected: true, repo: r.fullName, path: i.path, truncated: text.length > FILE_CAP, untrusted: true, content: text.slice(0, FILE_CAP) };
```

- `repoRow` lookup is by exact `fullName`; `defaultBranch` comes from the DB row (D-02). Default branches with `/` in the name: encode per segment like paths (LOW confidence that GitHub resolves `%2F` in `tree_sha`; see Open Questions).
- `get()` returns `{ status: 304 }` only when an etag is passed; we never pass one, but narrow on `res.status === 200` to satisfy TS (as `getPullRequest` does).
- Map `GithubError` inside the handler to an honest `ToolError`: `not_found` → `"Not found on the default branch: {path}"`; `client` 403 → `"GitHub refused: the read token may need Contents: Read-only."` (owner action already logged). Otherwise the gateway turns it into the generic `"Tool failed"`.
- Output shape: give `list_tree` its own output schema `{ connected, message?, repo, branch, truncated, entries: {path,type,size?}[] }` rather than forcing `listOut` — both tools are new.
- `list_tree` optional `prefix` (validated with `repoPath`): filter `entries` to `path === prefix || path.startsWith(prefix + "/")`; drop `NOISE` matches; `truncated = gh.truncated || kept.length > TREE_CAP`.

### Pattern 2: Tool input schemas the model sees

`toAnthropicTool` calls `z.toJSONSchema(tool.input)` in default (output) mode. Verified this session with zod 4.6.5:
- a `.transform()` anywhere in the input **throws** "Transforms cannot be represented in JSON Schema" (so `projectInput` cannot be used whole: `workspacePath`/`workspaceMachine` use `optText` with a transform — `.pick()` only name/description/context/category/priority/targetDate, which also enforces D-09's "not settable");
- fields with `.default()` are emitted as **required**, so the model is told to fill every task's `dueDate`, `priority`, `milestoneRef`… on 40 tasks (output tokens).

Recommendation: write the agent-facing draft schema with `.optional()` / `.nullable().optional()` and apply defaults when building the approval payload (or pass `{ io: "input" }` in `toAnthropicTool`, a one-line global change verified to make defaulted fields optional and tolerate transforms; it only affects what the model is told). Prefer the global `io: "input"` one-liner — it fixes the same latent issue for every tool — and keep `tests/unit/agent-contracts.test.ts` green.

### Pattern 3: D-06 content floor (gateway tier step)

```typescript
// src/server/agents/gateway.ts, Step 3
const CONTENT_TOOLS = ["github.get_file", "github.list_tree"];
let tier = resolvePolicy(tool.tier, ov?.tier);
if (tool.sideEffect && (tier === "READ" || tier === "PREPARE" || tier === "EXECUTE")) {
  const [seen] = await h.select({ id: toolCalls.id }).from(toolCalls)
    .where(and(eq(toolCalls.runId, runId), inArray(toolCalls.tool, CONTENT_TOOLS))).limit(1);
  if (seen) tier = "APPROVE"; // repo content can only ever produce a proposal (D-06)
}
```
- Put the pure decision in `policy.ts` (`withContentFloor(tier, sideEffect, sawContent)`) so `tests/unit/policy.test.ts` covers it; the query stays in the gateway.
- The write tools also refuse to run without `ctx.approvalId` (copy `needApproval` from `tools/calendar.ts`), so an owner override to EXECUTE can never make `projects.create` write unreviewed — consistent with D-08.
- Scope gap (see Open Questions): the query is per run. Sibling child runs under the same orchestrator run are not covered; widening to `run_id in (select id from agent_runs where id = $run or parent_run_id = (select parent_run_id from agent_runs where id = $run))` is one subquery and still honours "at least APPROVE".

### Pattern 4: Composite write tools + one transactional executor

**Payload (shared draft, `src/lib/project-payload.ts`, client-safe):**
```typescript
const ref = z.string().min(1).max(40);               // NOT "key": redact() blanks /key/i field names
const fields = projectInput.pick({ name: true, description: true, context: true, category: true, priority: true, targetDate: true });
```

**Tool shells (`src/server/agents/tools/projects.ts`):** `tier: "APPROVE"`, `sideEffect: true`, `private: true` (owner data, taints like the Phase 5 reads). `resolve(i, ctx)`:
1. every repo link `repo` exists in `github_repos` (else `ToolError("not_found")` → the agent sees it before an approval is made);
2. `sources` = this run's `tool_calls` rows for `github.get_file`/`github.list_tree` (status `done`) mapped to `"owner/repo · path"` / `"owner/repo · (file list)"` — server-derived, overwriting anything the model sent;
3. update only: load the project (not found → `not_found`), every `id` belongs to it, build `before` (name, `updatedAt` ISO, current field values, current title/due/priority/milestone of the touched items).
`toApproval({ reason, ...payload })` → `{ payload: schema.parse(payload), reason }` (calendar pattern).

**Executor:**
```typescript
async function applyDraft(ctx: ToolContext, kind: "create" | "update", p: Draft): Promise<Out> {
  needApproval(ctx);
  const action = kind === "create" ? "project.agent_create" : "project.agent_update";
  const now = ctx.now();
  return ctx.handle.transaction(async (tx) => {
    // D-11: idempotent on retry (cheap enough to check always, not only when ctx.adopt)
    const [done] = await tx.select({ m: auditLog.metadata }).from(auditLog)
      .where(and(eq(auditLog.action, action), eq(auditLog.target, ctx.approvalId!)));
    if (done) return done.m!.result as Out;
    const ok = <T extends { ok: boolean }>(r: T, what: string): Extract<T, { ok: true }> => {
      if (r.ok) return r as Extract<T, { ok: true }>;
      const e = "errors" in r ? Object.values(r.errors as Record<string, string>)[0] : "not found";
      throw new ToolError("invalid_input", `${what}: ${e}`); // throw → rollback; ToolError → definite failure
    };
    // create: createProject(tx, {...fields}) ; update: updateProject(tx, id, { ...currentRowAsProjectInput, ...changes })
    // milestones: createMilestone / updateMilestone(tx, id, { ...current, ...edit }) → refMap
    // tasks: createTask(tx, { title, dueDate, priority, projectId, milestoneId }) / updateTask(tx, id, { ...currentAsTaskInput, ...edit, projectId })
    // links: githubRepos by fullName → addLink(tx, projectId, { kind: "repo", repoId }) | addLink(tx, projectId, urlLink)
    // deps: addTaskDependency(tx, taskId, blockedById, now)
    const result = { projectId, name, url: `/projects/${projectId}`, counts };
    await tx.insert(auditLog).values({ actor: "agent:projects", action, target: ctx.approvalId!, metadata: { approvalId: ctx.approvalId, projectId, result } });
    return result;
  });
}
```
- Update `stale` check inside the tx: if `projects.updatedAt` ≠ `before.updatedAt` → `ToolError("invalid_input", "This project changed after the request was prepared…")`; `toDTOs` computes `targetChanged` for `project_update` the same way (one extra query, mirrors the event etag logic) so the card disables approve.
- Output schema: `z.object({ projectId: z.uuid(), name: z.string(), url: z.string(), counts: … })` — no field names matching the redact regex.

### Anti-Patterns to Avoid
- **Payload field names containing `key`/`token`/`secret`/`password`/`authorization`:** `redact()` replaces their values with `"[redacted]"` in `tool_calls.input/output` (trace and model-visible duplicate answers).
- **Calling `updateProject`/`updateTask`/`updateMilestone` with only the changed fields:** they parse with defaults and overwrite everything (workspace path, notes, remindAt, context).
- **Letting the model supply `sources`, `before`, `projectId` changes or repo ids:** server builds them in `resolve`, `LOCKED` keeps them.
- **Rendering `context` or repo text as Markdown/HTML:** plain `whitespace-pre-wrap` text only (UI-SPEC).
- **One `get_file` per turn:** cumulative input tokens grow per turn (only the system prompt is cached); the prompt must ask for parallel `get_file` calls in one turn.

## Common Pitfalls

### Pitfall 1: Non-throwing server functions inside the transaction
**What goes wrong:** `createTask` etc. return `{ ok:false, errors }`; if the handler ignores it the tx commits a partial project.
**How to avoid:** `ok(result, label)` helper throws `ToolError` on any non-ok → rollback → `executeApproved` marks `failed` (definite, not ambiguous). DB test: second task invalid (e.g. a dangling milestone id in an update) → zero rows in projects/milestones/tasks/links/audit.

### Pitfall 2: Swallowed errors that abort the transaction
**What goes wrong:** `aud()` and `notifyLive()` catch their own errors without a savepoint; in Postgres a failed statement aborts the whole tx and every later statement fails ("current transaction is aborted"). `addLink`'s unique-violation catch has the same shape.
**How to avoid:** Prevent the conditions: dedupe repo links in `refsResolve` (unique `repo`), validate refs up front. Any such abort still ends in a rollback (safe), just with a generic ambiguous error. `emitActivity` is fine: it uses its own `h.transaction` → savepoint.

### Pitfall 3: Full-replace updates
**What goes wrong:** Agent update sends `{ name }` → `updateProject` defaults `workspacePath`/`workspaceMachine` to null, `blockerNote`/`context` to "", `status` to active. `updateTask` without `notes`/`remindAt` clears them.
**How to avoid:** Build the full input from the current row, then overlay the edit; pass `projectId` explicitly to `updateTask` (it keeps refs only when `projectId` is absent).

### Pitfall 4: `turnMaxTokens` 4096 truncates the big tool call
**What goes wrong:** A 40-task + 12-milestone + 4000-char-context `projects.create` is roughly 2.5–3.5k output tokens plus any preamble; at 4096 the turn can stop with `max_tokens` mid-`tool_use`, giving an invalid/partial input → zod reject → the model re-emits the whole draft (doubling cost) or the run hits limits. [ASSUMED estimate: ~4 chars/token]
**How to avoid:** Projects `limits.turnMaxTokens: 8192`.

### Pitfall 5: Orchestrator `activeMs` includes the delegate's child time
**What goes wrong:** In `advance()`, `active += now() - t0` runs after the tool loop, so an inline `delegate` (child runs Sonnet turns, incl. a ~3k-token generation) counts toward the **orchestrator's** 120 s. If the child took > ~110 s, the orchestrator resumes after approval and immediately fails "This run took too long and was stopped." — the project exists, but D-16's reply is lost. [VERIFIED by reading loop.ts; not reproduced]
**How to avoid:** Time the delegate call and subtract it (`if (use.name === "delegate") childMs += now() - c0;` then `active += now() - t0 - childMs`), ~3 lines; plus projects `activeMs: 240_000`. Add a loop DB test with a fake clock advancing during the child.

### Pitfall 6: Token budget grows per turn
**What goes wrong:** `tokens` sums each turn's uncached input; history is re-sent every turn (only the system prompt has `cache_control`). One file per turn: ~3k, 9k, 13k … ≈ 180k cumulative for tree + 6 files → over 150k.
**How to avoid:** Prompt (D-19): "Call list_tree once, then request README and up to 5 other files in ONE turn (parallel tool calls), then call projects.create." Fake-LLM DB test uses that shape.

### Pitfall 7: Existing tests that hard-code tool counts/tiers
`tests/db/github-tools.test.ts` asserts 6 READ github tools (→ 8). `tests/db/project-tools.test.ts` asserts every `projectTools` entry is READ/side-effect free (→ filter to the two reads). `tests/unit/agent-contracts.test.ts` checks the projects tool list and api-name regex (`github_list_tree`, `projects_create` pass).

### Pitfall 8: Fine-grained PAT without Contents permission
**What goes wrong:** Trees and contents need Contents: Read for private repos [CITED: docs.github.com/en/rest/git/trees — "contents:read"; MEDIUM, via search summary]; missing permission yields 403/404 that the gateway would report as "Tool failed".
**How to avoid:** Map `GithubError` in both handlers to explicit messages (Pattern 1). Owner action already logged.

### Pitfall 9: GitHub content edge cases
Directory path → array response; symlink/submodule → `type` ≠ `file`; 1–100 MB → `content: ""`, `encoding: "none"`; recursive tree truncated beyond 100,000 entries / 7 MB [CITED: GitHub REST docs]. All handled by Pattern 1.

### Pitfall 10: e2e has no LLM and no worker
**What goes wrong:** D-20 says "e2e with the existing fake LLM", but `scriptedLlm` lives in `tests/helpers` for vitest; the Playwright server runs with no `ANTHROPIC_API_KEY` and no worker (`approvals.spec.ts`: "No worker in e2e").
**How to avoid:** Split SC3 proof: (a) DB integration test drives the Studio prompt with `scriptedLlm` + `fakeGithub` through `createRun`/`advance` → one approval → `decide(edited)` → `executeApproved` → `runQueued` → project complete + reply contains `/projects/<id>`; (b) e2e seeds a `project_create` approval (new `insertProjectApproval` in `tests/e2e/owner.ts`, modelled on `insertApproval`), edits (removes a task, renames), approves → card shows `Creating the project…` and DB `edited_payload` lacks the task; then seeds an executed approval + the created rows (or runs the same SQL the executor would) to check `Open project` → `/projects/{id}` shows context card, tasks, milestones, repo link.

### Pitfall 11: Client-safe boundary
`src/lib/approval-kinds.ts` and `project-payload.ts` are imported by client components; keep the draft schemas import-free of `@/server/*` (approval-kinds already imports `@/server/time`, which is client-safe today — don't add more).

## Open Questions (RESOLVED)

1. **Default branch names containing `/` in the trees endpoint**
   - What we know: `tree_sha` accepts "SHA1 or ref (branch or tag) name" [CITED]. Contents uses `?ref=` (query, safe).
   - What's unclear: whether `%2F`-encoded or raw-slash branch names resolve in the path segment.
   - Recommendation: encode per segment (keep `/`); if a 404 appears in UAT, fall back to `GET /repos/{o}/{r}/branches/{branch}` → `commit.commit.tree.sha`. Not worth code now (default branches are main/master).
   - RESOLVED: deferred to UAT. Plan 02 encodes the branch segment; main/master are unaffected; a 404 in UAT becomes a gap.
2. **Content floor scope (per run vs run tree)**
   - What we know: D-06 says "in that run"; the Projects agent's write tools need approval regardless; floor only matters if the owner lowers a tier.
   - What's unclear: a second delegated child of the same orchestrator run (or a later thread turn) could carry repo-derived text without being floored.
   - Recommendation: widen the gateway query to the run plus its siblings under the same parent (one subquery, still "at least APPROVE"); leave thread-level carry-over as residual risk documented in docs/permissions.md.
   - RESOLVED: sibling-run content floor implemented in plan 03 (withContentFloor + run-tree query); residual thread-level risk documented in plan 08.
3. **Audit actor for agent-executed writes**
   - What we know: `projects.ts`/`tasks.ts` `aud()` hard-code `actor: "owner"`.
   - Recommendation: leave (owner approved them; D-10 says "exactly like owner writes"); the D-11 marker row carries `actor: "agent:projects"` and the approval id for traceability.
   - RESOLVED: plan 05 writes the `agent:projects` audit marker (project.agent_create / project.agent_update, target = approval id) inside the transaction; owner-style aud rows unchanged.

## Security Domain

### Applicable ASVS Categories (Level 1)

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (unchanged) | better-auth owner session |
| V3 Session Management | no | — |
| V4 Access Control | yes | `requireOwner` on existing approval/project actions; agent tool allow-list; content tools restricted to `github_repos` rows; write tools require `approvalId`; D-06 floor |
| V5 Input Validation | yes | zod draft schemas on tool input, at approval creation (`toApproval` parse) and on approve/edit (`payloadSchemaFor`); repo path regex + per-segment encoding; `checkPath` blocks host change |
| V6 Cryptography | no | read PAT stays in the existing encrypted `connections` store |
| V8 Data Protection | yes | private-repo taint (D-05); write tools `private: true`; `redact()` on stored I/O; agent never sees/sets `workspacePath` |
| V12 Files/Resources | yes | size caps (1 MB GitHub, 16K returned, 400 entries), binary refusal |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Indirect prompt injection via README/docs (OWASP LLM01) | Tampering / Elevation | `untrusted: true` envelope inside `<tool_data>` (existing `<` escaping), prompt rule, D-06 floor, approval + edit before any write, sources shown on the card |
| Path traversal / SSRF through `path` | Tampering | relative-path validation, `encodeURIComponent` per segment, fixed `BASE`, `checkPath` |
| Shell injection through workspace path | Elevation | `workspacePath`/`workspaceMachine` excluded from agent schemas (`.pick`) |
| Malicious URLs in drafted links | Spoofing | `linkInput` http/https refine; links non-clickable in the preview; Phase 5 `safe-url` on the project page |
| XSS via drafted context/description | Tampering | React text rendering, no Markdown/HTML (UI-SPEC) |
| Private content to free model | Information disclosure | `mentionsSensitive` on `repo` in every output (D-05) |
| Resource exhaustion (huge trees/files/drafts) | DoS | caps; draft bounds 12/40/10; per-agent limits; spend cap unchanged |
| Duplicate creation on retry | Tampering | D-11 audit marker in the same tx |
| Owner edit changing a repo link target | Tampering | links-subset lock (D-15) server-side |
