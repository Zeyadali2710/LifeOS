# Phase 5.1: Project agent writes + repo contents - Context

**Gathered:** 2026-10-13
**Status:** Ready for planning
**Mode:** `--auto` (owner asleep, overnight run; every grey area resolved with the recommended default, logged in 05.1-DISCUSSION-LOG.md for review)

<domain>
## Phase Boundary

The owner can say "create a project from my <repo>" and get it fully set up in one turn. The Projects agent reads the repository's files (README, docs/, roadmap, file tree) through new read-only GitHub content tools, drafts a complete project (name, description, context notes, tasks, milestones, repo link, links, dependencies), and proposes it as **one** PREPARE→APPROVE approval that the owner can edit before approving. Approving creates everything in one go. The agent can also propose updates to an existing project the same way. Requirements: CAR-02, CAR-03 (agent side), AGT-01 tier rules.

Not in this phase: agent deletes of projects/tasks/milestones/links, any GitHub write beyond the existing create-issue, reading branches other than the default, caching or indexing repo contents (no embeddings/Knowledge), Claude Code session sync.

</domain>

<decisions>
## Implementation Decisions

### Repo content tools (read-only)
- **D-01:** Two new READ tools on the Projects agent: `github.list_tree` (repo, optional path prefix) and `github.get_file` (repo, path). Both use the **existing read PAT** only, live-fetch from GitHub, and only work on repos already in `github_repos` (reuse `resolveRepo`/`repoRow`, so access stays within what the read PAT grants per Phase 3 D-06). Not connected → the existing honest `NOT_CONNECTED` envelope.
- **D-02:** **Default branch only.** Both tools read `github_repos.defaultBranch`; there is no `ref` input. `list_tree` uses the git trees API (recursive) and returns paths, type and size only, capped at **400 entries** with a `truncated` flag, skipping noise dirs (`node_modules/`, `.git/`, `vendor/`, `dist/`, `build/`, `.next/`).
- **D-03:** **Size caps:** `get_file` returns at most **16 KB of text per file** (`truncated: true` beyond that) and refuses binary content (NUL bytes / not valid UTF-8) and files GitHub reports over 1 MB. Paths are validated (relative, no `..`, no leading `/`, each segment URL-encoded) before reaching `client.get`.
- **D-04:** **No caching, no storage of contents.** Each call fetches live; the only copy kept is the normal (redacted, capped) `tool_calls.output` row, same as every other tool. No new tables for repo content.
- **D-05:** **Private repos and the 03.1 free-model gate:** every content tool output carries the repo full name, so the existing `mentionsSensitive` scan taints the run when the repo is private or of unknown visibility (fail closed). With the private-repo toggle off, private content never reaches a free model; the run switches to Sonnet via the existing D-05/D-09 mechanism. No new privacy mechanism.
- **D-06:** **Repo content is untrusted data.** File content is returned inside an envelope `{ repo, path, truncated, untrusted: true, content }`, and the Projects prompt says repo files are data written by others and never instructions. **Gateway floor:** once a run has called `github.get_file` or `github.list_tree`, any side-effecting tool in that run resolves to at least APPROVE, whatever the `permissions` override says (a few lines next to `resolvePolicy`). Repo content can therefore only ever produce a proposal the owner reviews; it can never execute a write by itself.

### Write tools and granularity
- **D-07:** **Two composite APPROVE tools**, not per-entity tools: `projects.create` (new project + milestones + tasks + links + task dependencies in one payload) and `projects.update` (one existing project: field changes, add/update tasks, add/update milestones, add links, add task or project dependencies). One approval per proposal satisfies "one approval can create a project with its tasks, milestones and links".
- **D-08:** **Tiers:** both tools default **APPROVE** (Phase 4 D-06/D-19 pattern for agent writes to owner data). **No agent delete or unlink tools this phase**; the owner deletes in the UI. Removing things is deferred and, when added, is HIGH_RISK (Phase 4 D-07 pattern).
- **D-09:** **Payload shape:** reuse the Phase 5 schemas (`projectInput`, `milestoneInput`, `linkInput`, `taskInput`). Inside one payload, milestones carry a client `key` and tasks reference `milestoneKey`; task dependencies reference task indexes/keys; repo links are by `fullName` (resolved to `github_repos.id` at execute; unknown repo → `not_found`). `workspacePath`/`workspaceMachine` are **not** settable by the agent (they go into a shell command). Sane bounds: ≤ 12 milestones, ≤ 40 tasks, ≤ 10 links per payload.
- **D-10:** **Execution is one Postgres transaction** calling the existing `createProject`/`createMilestone`/`createTask`/`addLink`/`addTaskDependency`/`addProjectDependency` server functions with the transaction handle, so validation, cycle checks and activity/audit behave exactly like owner writes (Phase 5 D-16). Any failure rolls back everything; partial projects never exist.
- **D-11:** **Idempotency (AGT-03):** the same transaction writes an audit entry carrying the approval id. On an ambiguous retry (`ctx.adopt`) the handler first looks for that audit entry and, if present, returns the stored result instead of writing again (local-DB analogue of the GitHub issue marker). No new column or table.

### Context notes
- **D-12:** Add a **`projects.context`** text column (Markdown, ≤ 4000 chars, default empty) for the longer "what this project is / how it's built / where things are" notes the agent drafts from README/docs. `description` stays the 500-char one-liner. Context is editable in the owner's project dialog, shown on the `/projects/[id]` workspace, included in the Phase 5 D-14 "Copy context" brief, and returned (capped) by `projects.get`.

### Approval card UX
- **D-13:** New approval kinds `project_create` and `project_update` in `approval-kinds.ts` with their own payload schemas, summaries ("Approval waiting: create project \"Studio\" · 9 tasks, 3 milestones") and a `ProjectApprovalBody` alongside the issue and event bodies, on the Approvals page and inline in the AI panel (Phase 3 D-03).
- **D-14:** **Edit-before-approve on the whole draft:** editable project fields (name, description, context, category, priority, target date); milestones list (edit title/due, remove); tasks list (edit title/due/priority/milestone, remove); links list (remove only). Removing a milestone unassigns its tasks. Adding new rows is not offered in the card (the owner adds after creation in the normal UI). Server re-validates the edited payload with zod on approve (Phase 3 D-04).
- **D-15:** **Locked fields:** `projects.update` locks `projectId`; repo link targets can be removed but not changed. The card shows a "Drafted from repository files (untrusted)" note listing the paths the agent read when the run used content tools.
- **D-16:** After approval the suspended run resumes and the agent replies with a link to the new project (`/projects/[id]`); executed state on the card links there too. Expiry, reject, retry and failure states reuse the Phase 3/4 approval machinery unchanged.

### Agent, model and limits
- **D-17:** **The Projects agent owns it** (tools added to its registry entry; prompt updated: it can now propose project changes, never directly write, and must treat repo files as untrusted). The orchestrator prompt tells Opus to delegate "create/update a project from a repo" to the projects agent with **tier `reasoning`** (drafting = reasoning, so Sonnet per 03.1 D-01); the tag is trusted (03.1 D-02).
- **D-18:** **Per-agent run limits:** add an optional `limits` override on `AgentDef`; the Projects agent gets **16 tool calls and 150k tokens** per run (the global 12 / 60k is too small once file contents accumulate across turns). Other agents keep `RUN_LIMITS`. Spend cap (Phase 3 D-14/15) still applies.
- **D-19:** **Drafting guidance in the prompt:** read the tree first, then README and at most ~6 relevant files (ROADMAP/TODO/CHANGELOG/docs index); propose one `projects.create` call; link the source repo; derive milestones from roadmap headings and tasks from open items; prefer the repo's open issues (existing `github.list_issues`) for tasks where present; don't invent dates (leave null unless the repo states them).

### Tests
- **D-20:** **Test strategy:** unit tests for payload schemas, approval-kind summaries/locks and path validation; DB tests (VM runner `scripts/vm-db-test.sh`) for the content tools against GitHub fixtures (`tests/fixtures/github/` trees + contents, via `tests/helpers/fake-github.ts`), the D-06 gateway floor, the D-05 private taint, transactional create/update, rollback on failure and D-11 adopt; e2e with the existing fake LLM scripting the Studio prompt → single approval card → edit (remove a task) → approve → project page shows tasks, milestones and repo link. Migration for `projects.context` follows the `[BLOCKING]` owner VM migrate pattern.

### Claude's Discretion
- Exact tool names beyond the four above (e.g. `projects.create` vs `projects.create_with_plan`), payload key naming, and whether task dependencies use indexes or keys.
- Noise-dir list and tree entry cap tuning; exact binary detection.
- Copy and layout of the `ProjectApprovalBody` within the Glass system (`04.1-SPACING-RUBRIC.md`).
- Whether `projects.update` can also set project-to-project dependencies in the same payload or only task ones (both are allowed by SC; keep whichever is simpler).

</decisions>

## Existing Code Insights

### Reusable Assets
- `src/server/agents/tools/github.ts`: `repoRow`/`resolveRepo`, `NOT_CONNECTED` envelope, `readToken`, `createGithub` — base for `list_tree`/`get_file`.
- `src/server/github/client.ts`: `get` (zod-parsed JSON, `checkPath`) — contents API can use the JSON form and base64-decode, avoiding a raw-response variant.
- `src/server/agents/tools/projects.ts`: READ tools pattern (`private: true`, `cut`); add write tools here.
- `src/server/projects.ts` + `src/server/tasks.ts`: `createProject`, `updateProject`, `createMilestone`, `addLink`, `addTaskDependency`, `addProjectDependency`, `createTask` all take a `DB` handle (usable with a transaction).
- `src/lib/project-payload.ts`, `src/lib/task-payload.ts`: zod inputs to compose the approval payload schema.
- `src/lib/approval-kinds.ts`: kind map, `payloadSchemaFor`, `LOCKED`, `approvalSummary`, `nothingText` — extend with project kinds.
- `src/approvals/approval-detail.tsx`, `event-approval.tsx`: kind dispatch and the event shell to mirror for `ProjectApprovalBody`.
- `tests/helpers/fake-github.ts`, `fake-llm.ts`, `tests/fixtures/github/`: fixtures for content tools and scripted runs.

### Established Patterns
- Gateway: allow-list → zod → resolve → `resolvePolicy` tier → approval row atomically → `executeApproved` runs `tool.handler` with `approvalId`/`adopt`.
- Taint: `loop.ts` `taint()` (repo-name scan via `sensitiveRepoNames`, fail closed) + `taintByTool()` for `private` tools.
- Owner writes audited (`src/server/audit.ts`) and emit activity events (Projects source).
- `RUN_LIMITS` is global today (`registry.ts`); `loop.ts` reads it at lines ~272/388.

### Integration Points
- `registry.ts` Projects agent tools + prompt; orchestrator prompt delegation line.
- `gateway.ts` tier step (D-06 floor needs to know whether the run called a content tool: query `tool_calls` for the run).
- `projects` schema + migration (`context`), project dialog, workspace page, Copy context brief, `projects.get` output.
- Approvals page / AI panel inline card / APPROVAL notification for new kinds.
