# Phase 5.1: Code Review Report

**Reviewed:** 2026-10-13
**Depth:** standard (shared server files reviewed as a diff against `5c88d8a^`)
**Files Reviewed:** 34
**Status:** issues_found

## Summary

The server side mostly holds up. Every `{ok:false}` from the server functions goes through `must()` and throws, so `applyDraft` rolls back cleanly. `toApproval` re-parses data that `resolve` has already validated. `sources`, `projectId` and `before` come from the server and are locked in `checkLocked`. `repoPath` and per-segment `encodeURIComponent` close off traversal and query injection in `get_file`/`list_tree`. Merging project fields in `updateProject` starts from the current row, so it does not wipe fields.

The serious defects are in the **owner edit form** (`project-approval.tsx`):
- Opening EDIT and approving silently reassigns tasks to the first milestone.
- In `project_update`, editing nulls out the due date, priority and milestone of every existing task and milestone in the draft.

So the owner approves data the agent never proposed. The e2e tests miss this because every scripted task sets `milestoneRef`.

The D-06 content floor covers the run tree, including siblings and children, as designed. It does not cover the thread or retried runs, and it only treats `get_file`/`list_tree` as untrusted.

## Critical Issues

### CR-01: Edit form assigns every task without a milestone to the first milestone

**File:** `src/approvals/project-approval.tsx:53-56,67`
**Issue:** `keyOf(t.milestoneRef)` runs `ms.find((x) => x.ref === k || x.id === k)`. `milestoneRef` is `.nullable().optional()` with no default, so when the model leaves it out it is `undefined` in the stored jsonb. With `k === undefined`, `x.id === undefined` matches every create milestone (they have no `id`). In update, `x.ref === undefined` also matches every existing milestone that has no ref. The task then gets the first milestone's ref (verified: `keyOf(undefined)` returns `"m1"`). The Select shows that milestone, and `validateProjectDraft` writes it as `milestoneRef`. Any edit (for example removing one task) followed by APPROVE or DONE moves all unassigned tasks into milestone 1. In update, existing tasks also get reassigned. `tests/e2e/project-approval.spec.ts:31-33` always sets `milestoneRef`, so this is not covered.
**Fix:**
```ts
const keyOf = (k?: string | null) => {
  if (!k) return "";
  const m = ms.find((x) => (x.ref !== undefined && x.ref === k) || (x.id !== undefined && x.id === k));
  return m ? (m.ref ?? m.id ?? "") : k;
};
```
Add a unit test: a create payload with `milestones:[{ref:"m1"}]` and a task with no `milestoneRef` should still have no `milestoneRef` after `validateProjectDraft(toProjectDraft(p))`.

### CR-02: Editing a `project_update` approval wipes due date, priority and milestone on existing tasks and milestones

**File:** `src/approvals/project-approval.tsx:64-67,86-96` (consumed by `src/server/agents/tools/projects.ts:225,239,249,252`)
**Issue:** On the server, `undefined` means "keep current" (`t.dueDate === undefined ? ct.dueDate : t.dueDate`, and the same for `priority`, `milestoneRef` and milestone `dueDate`). The edit form turns `undefined` into `""` (`dueDate: t.dueDate ?? ""`, `priority: t.priority ? … : ""`), then into `null` (`dueDate: t.dueDate || null`, `priority: … : null`, `milestoneRef: … : null`, milestone `dueDate: m.dueDate || null`). `null` means "clear". Example: the agent proposes renaming existing task X (`{id, title}` only) and the owner edits anything on the card. Approving then clears X's due date, its priority, and its milestone (or moves it to milestone 1, see CR-01). The fields also render empty, so the owner cannot see their real values, which are in `before.tasks`/`before.milestones`. `sameProject`'s `norm` treats `null` and absent as equal, which hides this until some other field changes.
**Fix:** Fill rows for `id` items from `before`, and keep "untouched" separate from "cleared":
```ts
// toProjectDraft (update): fill from before when the draft omits the field
const b = isUpdate(p) ? p.before.tasks.find((x) => x.id === x0.id) : undefined;
dueDate: t.dueDate === undefined ? (b?.dueDate ?? "") : (t.dueDate ?? ""),
priority: t.priority === undefined ? (b?.priority ? String(b.priority) : "") : (t.priority ? String(t.priority) : ""),
milestone: t.milestoneRef === undefined ? (b?.milestoneId ?? "") : keyOf(t.milestoneRef),
```
Do the same for milestones from `before.milestones`. In `validateProjectDraft`, for `id` rows, leave out keys whose value equals the `before` value instead of sending `null`. Add a DB test: edit an update approval that only renames a dated task, approve, and assert that `dueDate`, `priority` and `milestoneId` are unchanged.

## Warnings

### WR-01: The content floor is scoped to the run tree, not the thread or retried runs

**File:** `src/server/agents/gateway.ts:117-135`
**Issue:** The floor only looks at `tool_calls` in self, parent, siblings and children. Content read by a child flows into the orchestrator's answer, and that answer is appended to the thread (`loop.ts:376`). The next orchestrator run in the same thread gets it through `threadHistory`, but its tree has no content-tool rows. Any side-effecting tool the owner has set to EXECUTE then runs without approval. `retryRun` (`loop.ts:449`) also creates the new run with no `parentRunId`, so retrying a failed projects child drops the floor. The privacy taint already handles both cases (`privateInTree`, `retryOf`, `privacyAnchor`), so the floor is narrower than the taint next to it.
**Fix:** Make the floor's run set match the taint's run set. Include runs whose `thread_id` matches this run's thread (or its root's thread), and the tree of `retry_of`/`privacyAnchor`. Alternatively, record a `contentTainted` flag on `agent_runs` and carry it forward the same way `privateTainted` is.

### WR-02: Only `get_file`/`list_tree` count as untrusted, and provenance only covers the current run

**File:** `src/server/agents/policy.ts:9`, `src/server/agents/tools/projects.ts:106-119`
**Issue:**
- `CONTENT_TOOLS` leaves out `github.get_pull_request` (third-party PR body) and `github.list_issues` (third-party issue titles). The new prompt explicitly tells the agent to turn issues into tasks (`registry.ts:57`), so an injection in an issue title gets around both the floor and the "untrusted" banner.
- `runSources` filters on `ctx.runId` only. If one projects child reads files and a second sibling child drafts from the orchestrator's summary, `sources` is `[]` and the card shows no "Drafted from repository files" warning. Meanwhile the gateway floor (tree-scoped) already knows content was read.

**Fix:** Add the third-party-text tools to the floor's set, or add a separate `UNTRUSTED_TOOLS` list. Build `runSources` with the same tree query the gateway uses.

### WR-03: Lost update — owner edits to tasks or milestones after drafting are silently reverted

**File:** `src/server/agents/tools/projects.ts:170,224-258`
**Issue:** The only staleness check is `projects.updatedAt`. `updateTask`/`updateMilestone` do not bump the project's `updatedAt`, and `before.tasks`/`before.milestones` are captured but never compared at execute time. `draftTask.title` is required, so even a due-date-only proposal rewrites the title. Example: the owner renames task X after the draft and then approves. X goes back to the drafted title.
**Fix:** In `applyDraft`, for each `id` row, compare the current row against the `before` entry (title, dueDate, priority, milestoneId) and throw `CHANGED` on mismatch. Do the same in `toDTOs` so the card shows it as stale.

### WR-04: An update that re-links an already linked repo fails the whole approval after the owner approves

**File:** `src/server/agents/tools/projects.ts:266-274`, `src/server/projects.ts:201-202`
**Issue:** `addLink` returns `{ok:false, errors:{repoId:"Already linked."}}`, and `must` turns that into a rollback. The prompt says "Link the source repository", so an update on a project that is already linked fails only at execute time. `resolve` (`checkRepos`) does not check for existing links, so the owner approves something that cannot apply.
**Fix:** In `updateTool.resolve`, reject links (or drop them with a note) that already exist on `cur.id`. Alternatively, skip existing repo links in `applyDraft` instead of failing.

### WR-05: `get_file` truncation can split a surrogate pair, and the cap counts characters, not bytes

**File:** `src/server/agents/tools/github.ts:338`
**Issue:** `text.slice(0, FILE_CAP)` cuts UTF-16 code units. An emoji or astral character that straddles 16384 leaves a lone high surrogate. `JSON.stringify` emits it as `\udXXX`, which Postgres `jsonb` rejects ("Unicode low surrogate must follow a high surrogate"). `finish()` in `gateway.ts:215` then throws outside the handler's try, and the run fails instead of returning a tool error. D-03 also specifies 16 KB; this caps at 16k characters, which can be up to about 48 KB of UTF-8.
**Fix:**
```ts
const bytes = buf.subarray(0, FILE_CAP);
const text = new TextDecoder("utf-8").decode(bytes).replace(/�$/, "");
// truncated: buf.length > FILE_CAP
```
Run the strict-UTF-8 validity check on the full buffer before truncating.

### WR-06: The read-only update diff shows omitted fields as being cleared

**File:** `src/approvals/project-approval.tsx:345,353-355`
**Issue:** `b.dueDate !== (t.dueDate ?? null)`, `b.priority !== (t.priority ?? null)` and `(b.milestoneId ?? null) !== (t.milestoneRef ?? null)` treat an omitted field (`undefined`, meaning keep) as `null`. A rename-only proposal therefore shows "3 Nov → No due date · P1 → None · milestone changes". The server keeps all three, so the owner is shown changes that will not happen. This is the mirror image of CR-02.
**Fix:** Only compare a field when `t.<field> !== undefined`.

### WR-07: The milestone Select shows "No milestone" for existing-milestone refs not in the payload, but keeps them

**File:** `src/approvals/project-approval.tsx:571`
**Issue:** In update, a task's `milestoneRef` can be the UUID of an existing milestone that is not in `p.milestones`. `live.some(...)` is false, so the Select shows "No milestone", but `t.milestone` still holds the UUID and `validateProjectDraft` sends it. The owner sees one thing and approves another, and cannot pick that milestone.
**Fix:** Add existing milestones from `before.milestones` (or a server-supplied list) to the options. At minimum, render the current value as a selectable option.

### WR-08: `toApproval` runs outside error handling in the gateway

**File:** `src/server/agents/gateway.ts:143,162`
**Issue:** The new project tools call `projectCreatePayload.parse`/`projectUpdatePayload.parse` in `toApproval`, and that runs twice outside any try. Today `resolve` validates the same shape first, but any drift between the `resolve` and `toApproval` inputs would throw a raw `ZodError` out of `callTool` and fail the whole run, instead of recording a failed tool call the model can correct. One such drift already exists: `resolve` validates with `sources: []`, while `toApproval` validates with the real sources.
**Fix:** Compute `const ap = tool.toApproval?.(input)` once, inside a try that maps errors to `reject(...)`, and reuse `ap.payload`/`ap.reason`.

## Info

### IN-01: `projects.update` name lookup can pick an arbitrary project

**File:** `src/server/agents/tools/projects.ts:337-339`
**Issue:** `ilike(name)` with `.limit(1)` and no order picks any one of several case-insensitive matches. The card shows `before.name`, which is the same for all of them.
**Fix:** If more than one row matches, throw `invalid_input` and ask for the id.

### IN-02: Repo link dedupe is case-insensitive, but the lookup is case-sensitive

**File:** `src/lib/project-payload.ts:150`, `src/server/agents/tools/projects.ts:136,271`
**Issue:** `Owner/Repo` passes the dedupe and then fails with `Unknown repository` against the stored `owner/repo`.
**Fix:** Use `ilike`/`lower()` in `checkRepos` and in the `applyDraft` repo lookup.

### IN-03: The AI panel card and the approval list show the old name for a proposed rename

**File:** `src/shell/ai/approval-card.tsx` (`pjName`), `src/approvals/approval-list.tsx:116`
**Issue:** Both use `before.name` even when `changes.name` is set. The detail view (`projectResolved`) already prefers `changes.name`.
**Fix:** Use `p.changes.name ?? p.before.name` for display.

### IN-04: Agent-initiated task and milestone writes are audited as `owner`

**File:** `src/server/tasks.ts:14-16` (via `applyDraft`)
**Issue:** Per-entity audit rows say `actor: "owner"`. Only the single `project.agent_*` marker records the agent. This follows D-10 ("behave exactly like owner writes"), but it makes it harder to trace who did what.
**Fix:** Optionally thread an actor through, or link the per-entity rows to the marker's approval id.
